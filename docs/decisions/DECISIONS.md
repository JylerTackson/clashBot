# Decision log

Every project decision gets an entry: id, date, status, who decided, the decision, and why.
Status values: **decided** (user or user-approved), **default** (Opus picked a conventional, reversible default; user may override), **proposed** (waiting on the user), **superseded**.

Process rules (from the user, 2026-10-28):
- Planning, auditing and re-planning are done by Opus. Implementation and every data edit are done by Sonnet, from Opus-written specs detailed enough that Sonnet makes no design decisions.
- Open questions go to the user before a decision is made.

Supporting documents: `docs/design/pipeline_review.md`, `docs/research/course_mapping.md`, `docs/data/data_audit_2026-10-28.md`.

### D-006 · Train/val/test split by video · default (Opus) · 2026-10-28
Samples from one game are near-duplicates; splitting by sample would leak. Split ≈70/15/15 by video, and exclude same-game neighbours during retrieval evaluation.

### D-007 · Two-speed retrieve-and-rank architecture · decided (user) · 2026-10-28
Fast loop every tick: hybrid retrieval over pro states + KG counter lookup + "hold" → legality filter → Laya/d1 ranker picks among ≤4 options → executor. Slow loop (Qwen, async): pre-game plan from pro context, plan updates every ~10 s or when a new enemy card appears, post-game reflection and memory writes. Reason: a generative LLM per decision costs ~1–4 s on a 16 GB Mac, longer than many defensive windows (pipeline review §3.1).

### D-008 · Clean dataset = game data + distilled pro advice · decided (user) · 2026-10-28
Keep: states, card/deck/KG facts, enrichment, creator insights, match lessons/card-usage/opponent sections (as documents). Drop from clean records: raw transcript lines (`commentary`), video titles/URLs, file-path refs. Keep one provenance table (game → video) for the report. Raw `knowledge_base/` stays as the untouched source layer.

### D-009 · Embedded storage, no servers · decided (user) · 2026-10-28
SQLite (records, KG tables, FTS5 for BM25) + numpy/hnswlib vector files + NetworkX (and later PyKEEN) for graph algorithms. Reason: lowest RAM next to YOLO + LLM on 16 GB; single-file database.

### D-010 · Action = card × lane × zone (+ hold) · decided (user) · 2026-10-28
Lanes: left (col ≤5) / middle (6–11) / right (≥12). Zones: back (row ≤4) / mid (5–11) / bridge (12–16) / enemy_half (≥17) — identical to `tools/extract_states.py`. Exact tile chosen afterwards from the pro's placement distribution for that card.

### D-011 · Repair + flag, never delete · decided (user) · 2026-10-28
Deterministic repairs where evidence exists (deck sanitising, unit side re-attribution by deck membership, opponent deck capped at the 8 most-played). Everything else is flagged. Flagged and `unknown` samples stay in the retrieval DB; samples with blocking flags are excluded from ranker training.

### D-012 · Opponent deck stays progressive per sample · default (Opus) · 2026-10-28
Each sample keeps only the opponent cards seen up to that moment (filtered to real cards, capped to the game's 8 most-played). Using the full game deck would leak future information that the live agent cannot have.

### D-013 · Derived data is rebuilt, not committed · default (Opus) · 2026-10-28
`dataset/` and `db/` are gitignored build outputs; they are regenerated by `tools/data/*` and `tools/db/seed.py` from `knowledge_base/` (deterministic, stdlib + numpy). Hand-authored inputs (e.g. `clashbot/resources/unit_map.json`) are committed. Reports are copied into `docs/data/` when reviewed.

### D-014 · Unit class → card mapping · default (Opus) · 2026-10-28
YOLO classes that are not card slugs are mapped by hand in `clashbot/resources/unit_map.json` (primary card, evolution flag, all candidate source cards). Ambiguous classes (`hog`, `bomb`, `goblin-ball`, `royal-guardian`, `axe`) get no primary card; their candidates come from game knowledge and the co-occurrence analysis in the audit (e.g. `goblin-brawler` co-occurs with Goblin Cage, lift 7.7).

### D-015 · Shared runtime package `clashbot/` · default (Opus) · 2026-10-28
Lane/zone rules, unit resolution, state-text rendering and feature vectors live in one importable package used by both the dataset builders and the live loop, so training and serving produce identical inputs (pipeline review §3.5).

### D-016 · Opponent deck comes from the curated match file · default (Opus review) · 2026-10-28
Supersedes the opponent-deck part of D-011/D-012's implementation. The per-game opponent deck is the match file's `opponent_deck_seen` (written by the Phase 4 review agents from video + commentary); perception play counts are used only to cap lists longer than 8 or when the match file has none. Per-sample `deck_known` = deck cards whose first observation is at or before the sample time. Reason: the play-count deck agreed with the curated deck on only 56% of cards and leaked the player's own cards into the opponent deck.

### D-017 · Deck registry = all 68 deck files · default (Opus review) · 2026-10-28
`deck_index.json` covers only the 19 RoyaleAPI-scraped decks; the other 49 deck files were created from the pro's games and carry most creator insights. The KG and documents use every deck file (frontmatter + `## Cards` links) and mark `in_index` on the node.

### D-018 · Separate "act now?" from "what to play" · default (Opus review) · 2026-10-28
Refines D-010. The ranker picks among play options only; holding is a separate binary act/hold head (both are fixed-answer tasks that suit Laya/d1). Reason: play samples are drawn at play moments, so hold-as-an-option is a free shortcut and its class prior is wrong. At runtime the trigger (`should_decide`) plus the act/hold head decide *when*; the ranker decides *what*.

### D-019 · Training candidates use "possible cards", not perceived legality · default (Opus review) · 2026-10-28
For dataset construction, a card is possible if it is a known hand card or (when any hand slot is unread) any other deck card; no elixir filter. The pro's action passed the perceived-legality check only ~54% of the time; mixing legal negatives with an "illegal" positive teaches the model perception artefacts. Runtime still filters by perceived legality (`legal_action_keys`).

### D-020 · Act/hold head needs denser negatives · noted limitation (Opus review) · 2026-10-28
The act/hold export is 92–93% "play" because pro samples are drawn around play moments, so `always_play` is already 0.92. A useful act head needs states where nothing was played; the dense 2 s perception timelines that could supply them were in the gitignored `runs/` folder and are not in this checkout. Plan: generate act/hold negatives from the user's own recorded games (or re-run perception on the videos on the Mac) before training that head. Until then, the runtime trigger rules (`should_decide`) decide when to act.

### D-022 · Fine-tune d1 first; data only for now · decided (user) · 2026-10-28

### D-023 · d1 data in its native Decision Index format, two variants · default (Opus) · 2026-10-28
d1 takes `(state, {name: question})` with `choice` / `noul` / `score` questions and reads one probability per option (model card + `prompt.py`, checked 2026-10-28). We export (a) **joint**: one `choice` question over the 4 candidate plays (1 pro + 3 hard negatives), matching the runtime re-ranking step; (b) **factorized**: three `choice` questions — card (possible cards), lane (3), zone (4) — answered in one pass, which avoids the 597-key label sparsity; (c) **act**: one `noul` question, provisional until D-020 is resolved. The request builder lives in `clashbot/d1_format.py` and is shared by the export and the future `D1Ranker`, so training and serving send identical requests. Which variant to fine-tune is decided at training time (good ablation for the report).

### D-024 · The "next" card is not a possible or legal play · decided (user) · 2026-10-28
`possible_cards` and the deck fallback of `legal_cards` exclude the next-slot card unless it is also read in the hand (contradictory reading → trust the hand). Audit: next-card reads are noisy — in 263 of 2,138 eligible plays with a next card outside the known hand, the pro played that very card, and 689 samples show it inside the hand. Those 263 plays become `skipped_pos_impossible` (≈4% of plays) under the existing D-019 rule.

### D-037 · The joint 4-way options leak the answer; rebuild as a 2×2 grid · decided (user) · 2026-11-02
A rule that looks only at the 4 option keys — pick the option that shares its card with another option and its lane+zone with another — scores 0.848 / 0.853 / 0.852 on train/val/test (random 0.25, best real baseline 0.37). Cause: the WP4 negatives N2 (same card, other zone) and N3 (other card, same lane+zone) are built around the positive, which is always the "intersection". Fine-tuning d1 on `d1/joint` as is would learn this shortcut. Until decided: every 4-way evaluation reports this `option_set_shortcut` baseline, and feature rankers use pointwise features only. **Decision (user):** rebuild the 4 options as a 2×2 card × placement grid — {pro card, second possible card} × {pro lane+zone, second legal lane+zone} — so every option shares its card with exactly one option and its placement with exactly one; the option-set rule is then at chance (0.25) by construction while the negatives stay hard. Package MAC-H; the ranker, baselines and d1 joint/factorized files are rebuilt at integration and every 4-way number is re-measured.
*Implementation note (default, Opus, 2026-11-02):* inside the grid, the second placement is drawn at random (seeded per example) within its block, because a fixed lane order made "right" a construction tell (lane-only rule 0.31 vs 0.25). FIX_LIST #13.

### D-041 · Live play timing: reactive rules until the learned act head is good · decided (user) · 2026-11-03
The live bot no longer plays on a periodic timer. It acts only to **defend** (enemy unit heading for our side or a new enemy play, timed by its ETA), to **avoid leaking elixir** (≥ 9.5), or to **punish** an opponent who just overspent (estimate ≤ 3) in the other lane; otherwise it holds and saves elixir. The chosen mode also filters the candidate plays (defend → threat lane, own half; punish → other lane, bridge/enemy side). The fine-tuned act head replaces/augments these rules once it beats them offline.

### D-048 · Knowledge graph v2: a game-model graph that feeds every decision · decided (user) · 2026-11-06
User: *"We should modulate all the data we have so that we can have a large Knowledge Graph … connect knight the stats of their specific level (but assume it is level 15) … create more connections as we find more cards in their deck through the pro player downloaded data … make sure we are utilizing the KG and KB to properly understand the game."* After the proposal: *"That sounds good, get this building now in parallel with fixers in queue and implementation checks."*

**Today.** KG v1 has 590 nodes and 12,030 edges, mostly wiki-text COUNTERS / SYNERGY plus 129 mined ANSWERED_BY edges. It holds no numeric stats, and decisions use only `counter_scores`. kNN retrieval copies one nearest pro state.

**KG v2 layers:**
1. Entities with per-level stats from the KB's own tables: opponents at level 15, ours at `levels.json`; spawned units; hero abilities; towers.
2. Mechanics edges computed by the lane simulation (MAC-AH): KILLS, STOPS, PULLS, damage prevented per elixir.
3. Empirical pro edges: thousands of ANSWERED_BY edges with held-rate, trade, and placement offset / timing relative to the attacker; PLAYED_AFTER; deck co-occurrence; situation aggregates.
4. An opponent-deck model that grows as cards are seen.

**Use.** The engine and policy take answers from the graph. Role transfer covers our cards that have no pro data. Placement comes from pro offsets. The LLM gets a compact facts block (D-045: the LLM decides), then is retrained on it.

**Process.** Packages MAC-AK K1–K4. Each report is audited against its spec before merge; failures go to FIX_LIST and to a queued fix agent.

### D-049 · The hero ability is used sparingly · decided (user) · 2026-11-07
**User:** "Not understanding how to properly use the musketeer hero ability, honestly this should be used very sparingly."

**Evidence.** In `runs/poc/20261106-233907` there were 6 Trusty Turret taps. In 4 of them the engine had not proposed the ability: the live loop offered it whenever the button was usable and the policy always added it to the allowed cards.

**Rule (MAC-AL P4).**
- The ability is an option only when the engine proposes it, which needs a simulated saving of ≥ 1,000 tower HP.
- The policy allows it only when no adequate card move for that push is affordable with its window open, or when the turret saves ≥ 1.5× what the best such card saves.
- At most one tap per 30 game seconds. Never as an emergency stand-in for another card.

D-045 holds: when offered, the LLM decides.
